# Spec：lint 告警基线清理（8 条 no-unused-vars 归零）

> 状态：待实现（未动手）。已建票：https://github.com/free5394/dns-clone/issues/2 （标签 `ready-for-agent`），本文件是它的正文。
> 上下文：`pnpm run lint` 实测 `Found 8 warnings and 0 errors.`（40 文件 / 136 规则 / 384ms，退出码 0）。
> 原始输出：`.scratch/lint-output.txt`（未跟踪，可重跑 `pnpm run lint` 复现）。

## Problem Statement

仓库在 `2116c6b` 接入 oxlint 时，全仓就已经存在 8 条 `no-unused-vars` 告警。当时按 `AGENTS.md` 准则 3「不要删除预先存在的死代码」主动留下一句「留作后续单独清理」，于是直到今天：

- `pnpm lint` 永远输出「8 warnings」，门禁的绿色信号里混着一段谁也没看过第二遍的噪音；新出现的第 9 条告警在这片噪音里根本看不出来。
- 这 8 条不是同一类东西，但输出里长得一模一样：4 条是真死代码（删了就完事），4 条是「我确实不关心这个值」被写成了会被误读为疏漏的形态（`catch (e)` 里 `e` 从没用过）。
- 想清理的人每次都要重新判断一遍哪条能删、哪条不能删、`catch` 该改成什么、`--fix` 为什么没用——这些判断做完就不见了，下一个人再从头做一遍。
- `oxlint --fix` 对这 8 条一条都修不了，所以不存在「顺手跑一下」的捷径，必须有人真的做决定。

## Solution

把 8 条告警按「真死代码」与「有意忽略但写法会被误读」两类一次性处置干净，`pnpm lint` 输出变成 `Found 0 warnings and 0 errors.`；处置口径与顺序写在下面，接手的人不需要再做判断。

- 只改源码，**不动 `.oxlintrc.json`**：不为这 3 个 catch 参数永久关掉 `no-unused-vars` 对 catch 的检查。
- 真死代码 → 删。有意忽略 → 改成仓库里已有的写法（可选绑定 `catch {}`、参数前缀 `_`），让「有意」在代码表面就能读出来。
- 唯一需要判断的一处（测试里只自增不读的计数器）→ **补断言而不是删**，因为它表达的正是「回退路径确实重新发起了请求」。
- 不改任何接口、契约、绑定、路由、cron 与数据库 schema。

## User Stories

1. 作为仓库维护者，我希望 `pnpm lint` 输出 `0 warnings / 0 errors`，以便把「干净」当作既成事实，而不是每次都要确认的一段例外。
2. 作为接手本次改动的 agent，我希望每条告警的处置理由都已经写在计划里，以便我不用重新判断哪条能删、哪条该保留。
3. 作为 CI，我希望静态检查步骤给出的绿色信号是确定的，以便门禁不被一串「已知告警」稀释，第 9 条新告警能立刻被看见。
4. 作为代码评审者，我希望这次改动的每一行都能追溯到某一条告警（或由它产生的孤儿注释），以便确认没有夹带行为变更。
5. 作为仓库维护者，我希望 `catch` 的写法统一到本仓库已有的形态（可选绑定），以便读到 `catch {}` 时立刻知道「这个错误是被有意忽略的」。
6. 作为仓库维护者，我希望 `scheduled` handler 那个有意不用的参数在名字上留痕，以便读者不会以为它被漏掉了。
7. 作为测试作者，我希望 IP 源回退用例保留「确实重新发起了请求」的断言，以便将来回退逻辑被改坏时测试会响。
8. 作为读者，我希望 DNS 记录重建函数上方的注释与它下面的代码说的是同一件事，以便不用去猜「防御性聚合」到底在哪一行。
9. 作为接手 agent，我希望计划按「是否可能改变行为或测试语义」排序，以便优先处理需要判断的两处、最后再做纯机械改写。
10. 作为仓库维护者，我希望这次改动不新增任何 lint 配置豁免，以便 `no-unused-vars` 在未来仍然对全仓其他位置生效。
11. 作为仓库维护者，我希望保留 `.oxlintrc.json` 里既有的 4 条豁免不动，以便这次清理不回退任何已定的规则取舍。
12. 作为未来的贡献者，我希望那几条实测结论（`--fix` 无效、下划线前缀对 catch 参数无效）留在仓库里，以便我不必重跑一遍探针。
13. 作为部署者，我希望这次改动不触碰任何一个运行时绑定、路由分支或 cron 配置，以便部署行为与改动前逐位一致。
14. 作为测试维护者，我希望本次不新增测试接缝（新文件、新脚本、新断言体系），以便测试结构的来源仍然唯一。
15. 作为仓库维护者，我希望验证方式就是仓库既有的 CI 四条命令，以便这次改动能直接进 CI 而不需要新增任何步骤。
16. 作为接手 agent，我希望 `catch {}` 这类改写被明确标注为「纯语法等价」，以便我知道它不需要新的测试断言。
17. 作为仓库维护者，我希望「把告警升级为 CI 硬门禁」这件事被显式排除在本 spec 之外，以便它作为独立的策略决定被单独评估。

## Implementation Decisions

**口径：只改源码，不动 lint 配置。**

- `.oxlintrc.json` 保持不变。理由：`no-unused-vars` 的交叉开关只有 `caughtErrors: "none"`（全局关掉对 catch 参数的检查）与 `varsIgnorePattern`（会把变量名改成带下划线的形态）；为了 3 个 catch 参数永久牺牲一类检查信号，代价大于在源码里各改 3 个字符。而 4 条真死代码无论如何都只能改源码，所以配置路线单独也到不了「归零」。
- 规则本身的既有豁免（`no-await-in-loop`、`unicorn/consistent-function-scoping`、`no-underscore-dangle`、`unicorn/no-array-sort`、`unicorn/prefer-set-has`）一条都不增不减。

**两组处置方式。**

- A 组（真死代码残留）：删除从未被读取的绑定与从未使用的导入。删除 `const x = await f(...)` 的**绑定**时保留 `await f(...)` 语句本身——执行顺序、错误传播与返回值都不变。
- B 组（有意忽略但写法会被误读）：保留「有意忽略」的语义，改成仓库既有形态。
  - `catch (e)` 里 `e` 未使用 → 改用**可选绑定** `catch {}`。不写 `catch (_e)`：下划线前缀只对函数参数生效，对 catch 参数无效（实测）。仓库已有 4 处可选绑定的先例，这不是新写法。
  - handler 里未使用的 `ctx: ExecutionContext` → 改为 `_ctx`，**不删参数**。它是 `scheduled` 的第三参契约位（Workers 的 ExecutionContext），保留位置与调用点形状一致。

**测试文件里两处的处置。**

- 未使用的导入 `FETCH_STRATEGIES` → 从 import 列表移除该标识符（该标识符在别处的使用不受影响）。
- 只自增、从不被读的 `callCount` → **补断言** `expect(callCount).toBeGreaterThan(1)`，与同文件既有兄弟用例同形；不删计数器。理由：这个计数器本来就是用来证明「主策略失败后确实重新发起了请求」，删掉等于把作者的测试意图一起扔掉。该断言在当前实现下必然成立（策略顺序为「先试已存策略、失败后按声明顺序回退」，该用例里已存策略返回空、回退策略命中，恰好 2 次请求）。
- 该断言是本 spec 唯一新增的断言，落在既有的测试文件与既有装配里，不引入新接缝。

**由本次改动产生的孤儿注释。**

- DNS 记录重建函数末尾那句注释声称「此处仅做防御性聚合」，但下面的代码只有 `return "success"`，被聚合的东西根本不存在；删除上面两个绑定后，这句注释彻底失去指代。处置：**改写为准确的一句**（说明「为什么不检查响应」——`processInChunks` 内部已对非 2xx 短路抛错），而不是直接删，因为它承载的是「这里为什么不需要再聚合」这个理由。

**不变更的东西。**

- 不新建、不重命名任何模块；不改任何模块的对外接口；不改数据库 schema、不改 API 契约、不改 cron 表达式与绑定名；不引入新依赖。

**定位速查**（行号会随代码漂移，请以符号名/函数名为准；此处仅为本次落点）

## Testing Decisions

**什么算好测试**：只断言对外可见的行为——CLI 的输出与退出码、公开函数的返回值、渲染出的 HTML、数据库里可见的状态；不断言内部实现细节（不 assert 某个私有变量、不 assert 调用了哪几个内部函数）。

**接缝：0 个新建。** 依次落在四个既有接缝上：

1. **`oxlint` CLI**（既有接缝，主接缝）：`pnpm lint` 的输出断言为 `Found 0 warnings and 0 errors.`。这是本 spec 的完成判据，不需要为它写任何测试文件。
2. **`test/sync.test.ts`**（既有文件）：覆盖 IP 源回退与策略持久化；本次唯一新增的断言就在这个文件里（见上）。先例是同文件 `:71` 的 `expect(callCount).toBeGreaterThan(1)`。
3. **`test/scheduled.test.ts`**（既有文件）：覆盖 `scheduled` 轮转与「同步抛错也照样翻转」的韧性；它以 `createExecutionContext()` + `worker.scheduled(controller, env, ctx)` 直接调用入口，正是参数改名后仍须保持绿色的守卫。
4. **`test/ui.test.ts` + `test/templates-escape.test.ts`**（既有文件）：覆盖模板渲染与转义。注意 `src/ui/templates.js` 不在 `tsc` 覆盖范围（`tsconfig.json` 把它排除），它的回归只能靠这两个文件。

**不做的事**：不新建 spec/断言脚本，不改 `vitest.config.ts`（必须保持 `maxWorkers: 1`），不为「纯语法等价」的 `catch {}` 改写新增断言。

**验证顺序（与 CI 一致）**：

```bash
pnpm cf-typegen   # 仅本地首次需要：worker-configuration.d.ts 被 .gitignore 排除
pnpm typecheck
pnpm lint         # 判据：Found 0 warnings and 0 errors.
pnpm format:check
pnpm test
```

**基线（已实测）**：`pnpm test` = 14 文件 / 154 项全绿（19.7s）；`pnpm lint` = 8 warnings / 0 errors；`pnpm typecheck` 本地可跑（`worker-configuration.d.ts` 已于本地生成）。

## Out of Scope

- `.oxlintrc.json` 的任何改动，包括新增 `caughtErrors` / `argsIgnorePattern` / `varsIgnorePattern` 豁免。
- 把告警升级为 CI 硬门禁（`oxlint` 加 `--max-warnings=0`，或把 `pnpm lint` 改成 `oxlint --deny-warnings`）。这是仓库级策略变更：一旦生效，未来任何一处「有意暂不使用」的变量都会挂掉 CI，需要单独决定，不在本次清理内。
- 为 `src/ui/templates.js` 里两个 `catch` 兜底分支补「坏 URL → 来源显示原始字符串」的断言。本次写成可选绑定是纯语法等价改写；该兜底行为目前没有任何测试断言（全仓测试里搜不到兜底文案），属于测试补强，另议。
- 其他静态检查 / 格式 / 类型问题——当前为 0。
- 任何行为变更、重构、命名风格统一、依赖升级。
- 把「告警基线」这类词收进 `GLOSSARY.md`：它是流程术语，不是领域语言，该文件只收领域词。
- 清理 `.scratch/` 下的探针文件与 lint 原始日志（未跟踪，不进版本控制）。

## Further Notes

- 这 8 条不是「新出现的问题」，而是 `2116c6b`（接入 oxlint + Prettier 并纳入 CI 门禁）按 `AGENTS.md` 准则 3「不要删除预先存在的死代码，除非被要求」主动留下的。本 spec 的存在本身就是那次留下的「后续单独清理」——**接手时不要再把准则 3 用在这里**，那一条针对的是「顺手清理无关死代码」，而这里是被明确要求的清理。
- 实测结论，免得重跑：
  - `oxlint --fix` 对 `no-unused-vars` 没有自动修复，8 条全部要手工改。
  - 下划线前缀对**函数参数**生效（`_ctx` 可以过），对 **catch 参数**不生效（`_e` 仍然报）。
  - 配置项 `caughtErrors: "none"` 可以一次性压掉全部 catch 参数告警——本 spec 明确选择不用它。
- CI 顺序是 `typecheck → lint → format:check → test`，且 `typecheck` 之前必须先跑 `cf-typegen`（`worker-configuration.d.ts` 被 `.gitignore` 排除，检出后不存在，缺它 `tsc` 会报找不到 `D1Database`）。
- `src/ui/templates.js` 是纯 JS 且被 `tsconfig.json` 排除，改动不受 `pnpm typecheck` 覆盖，只能靠测试与浏览器复验；它的格式归 `pnpm format` / `format:check` 管（glob 含 `src/**/*.{ts,js}`）。
- 本仓库的 `test/**` 不在 `tsconfig.json` 的 `include` 内，因此测试文件不参与 `pnpm typecheck`——但 vitest 会照常执行它们，改动仍须以 `pnpm test` 全绿为准。
